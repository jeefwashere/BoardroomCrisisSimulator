# Rehearsal audio conversation test guide

Use this guide with the isolated `experiment/ai-voice-playtest` application. It explains how to test recorded voices, a conversation with three test seats, turn permissions, live agents and one decision round. These are repeatable manual tests. A listed expected result is not a claim that your browser, microphone or every case has already passed.

## Start here

1. Open [the audio lab](http://127.0.0.1:8788/audio-lab) on the Mac running the test server.
2. Read the current budget display. Replaying an existing clip and loading its written text use no provider calls.
3. Run the recorded 90 second demo first. This creates three test seats in one window, plays their prepared lines, submits the corresponding script text, votes for a prepared option and finishes one consequence. It does not automatically call transcription or a live model.
4. Create a fresh room for a manual five minute conversation. Select each seat when you want to control it. During discussion, play a clip from the active speaker, then use your own seat to answer when its turn arrives.
5. Use the optional paid controls only when you want to test a live Vertex reply or ElevenLabs transcription. Export the result when finished.

The prerecorded speakers are fictional test fixtures. Their voices are generated by ElevenLabs Flash v2.5. They do not listen, improvise or decide what should happen next. You choose the clip and respond by typing or recording your microphone. The separate live agent buttons call Gemini 3.8 Flash with LOW reasoning. The application code controls turns, votes and outcomes.

## Choose the right kind of test

| Action | What actually runs | New provider reservation |
| --- | --- | --- |
| Play an available recording | Saved MP3 playback | None |
| Stop a recording | Local player and shared speech cancellation | None |
| Load a clip's written text | Copies the authored fixture caption into the editor | None; this is not speech recognition |
| Commit text or send room chat | Authenticated application command | None |
| Recorded 90 second demo | Scripted seats, saved clips and prepared votes | None |
| Transcribe a selected recording or microphone clip | ElevenLabs Scribe v2 | 400 speech credits reserved per request |
| Ask a live agent, extract, generate debrief or resolve a winning custom proposal | Vertex Gemini 3.8 Flash, LOW | US$0.05 reserved per model attempt |
| Compare all three characters after the round | Three concurrent Vertex requests | Up to US$0.15 reserved |
| Speak a live reply | ElevenLabs Flash v2.5, unless its exact audio is cached | Up to one speech credit per generated character |

The persistent speech cap is **30,000 credits** and the persistent Vertex test cap is **US$20**. Reservations are conservative application limits, not provider invoices. Failed calls stay reserved. Read the current page balance rather than assuming a fixed allowance remains. Do not delete either ledger or switch data directories to restore a balance.

## A five minute conversation you can perform yourself

Click New three seat room for a fresh room in manual mode. Leave all three test seats in this single window so their presence remains current. The first seat is the host and initially the CEO. Choose the normal five minute profile, then click Start manual round.

| Time from Start | Phase | What to do |
| --- | --- | --- |
| 0:00 to 0:15 | Briefing | Read the released MapleCart situation |
| 0:15 to 0:45 | Reading | Review the public context and choose discussion clips |
| 0:45 to 3:00 | Discussion | Speak, play a fixture or type during the current seat's turn; finish to hand over |
| 3:00 to 4:00 | Voting | Select each seat and cast its own ballot |
| 4:00 to 5:00 | Result and any resolution | Review the consequence; handle a tie or custom winner if needed |
| After 5:00 | Ended | Check the decision, optionally compare live characters, then export |

A workable conversation is:

1. First seat: play the owner and deadline clip, `discussion_owner`. Load its text only if you want that exact scripted contribution. Otherwise type your own answer: “I can contact IT. What evidence do we need before promising recovery?” Commit while the first seat has the floor, then finish its turn.
2. Second seat: play `discussion_containment`. Respond as this seat: “Preserve the logs, isolate the affected finance device and keep unaffected checkout under observation.” Commit, then finish.
3. Third seat: play `discussion_public_update`. Respond: “Separate confirmed facts from unknowns. Who owns the next public update?” Commit, then finish.
4. Once the ordered speaking slots are finished, open discussion permits any eligible seat to contribute. Use it for follow up questions. Selecting a different seat changes which authenticated participant sends the next command.
5. During voting, have all three seats choose the same prepared option for the simplest first run. Each ballot is a separate command; saying a preference aloud does not cast it.
6. After the result, check that only one consequence was committed. Optional live review asks how the models describe that recorded consequence.

The application does not infer an answer from playback. Playing a clip, committing its text, submitting a question to an agent and voting are separate actions. A contribution typed from the known script remains labelled typed, even if you also listened to the recording. Use the transcription control when you want an actual audio recognition test.

## A01: Repeat the zero call recorded demo

1. Note the speech and Vertex reservation balances.
2. Click Run recorded 90s demo and leave the page visible. If the browser blocks audio, use its visible Play control; do not count inaudible autoplay as a playback pass.
3. Observe the active seat, clip caption, committed contribution and handoff for each of the three seats.
4. Wait until the round ends, then export the result.
5. Repeat in a fresh room and compare the balances.

Pass: three distinct memberships, three scripted contributions, prepared ballots and one consequence appear. The demo remains labelled scripted, and neither provider balance increases from the demo itself. A paused or blocked player must not silently commit a different seat's contribution after its turn has expired.

## A02: Preview the recording library

1. Create a room and stay in the lobby.
2. Select clips from several roles or groups. Read the captions and play each one explicitly.
3. Stop a clip midway, then replay it.
4. Compare the displayed duration, caption and audible words.

Pass: only available saved recordings can be played; replay makes no new generation request. Captions identify the exact script. The library does not invent a future scenario outcome or present a prerecorded line as a live Gemini response. If the file is unavailable, record Blocked with its clip ID.

## A03: Verify turn permissions

1. Start a manual five minute room and wait for discussion.
2. While the first seat has the floor, select the second seat and try to commit a contribution, play a recording or request transcription.
3. Return to the active seat and perform the same action.
4. Finish the active seat's turn and observe the next speaker.

Pass: the inactive seat is disabled or rejected for actions that require the speaking turn. The active seat succeeds. A failed attempt does not add a contribution, ballot or outcome. A prerecorded voice saying “it is my turn” cannot change server eligibility.

Custom proposals have a separate rule: any eligible participant may save a proposal during discussion. Do not mark that as a turn permission failure simply because another seat is currently speaking.

## A04: Cancel audio and test a phase change

1. Start a saved clip during an eligible speaking turn.
2. Use Stop room audio. Confirm that playback halts and the old audio lease is no longer usable.
3. Play another clip and finish the current turn while it is playing, or let the speaking slot expire.
4. In another run, let discussion change to voting during playback.

Pass: the player stops after the application observes the changed lease, turn or phase. The UI polls, so cancellation is not a sample accurate audio guarantee. Playback never extends the speaking slot or pauses the round clock.

## A05: Host skip and ordered speaking

1. During discussion, select the host and use Skip speaker.
2. Verify that the current speaker changes and its old playback stops.
3. Try to finish a turn from a seat that is not the speaker.

Pass: the host may skip the current speaker. An ordinary seat can finish only its own active turn. The application still controls speaking order; an audio handoff line alone has no authority.

## A06: Free caption loading versus real transcription

1. In the lobby, choose a clip and load its written text into the editor.
2. Edit that text. Confirm that no contribution has been committed yet and no speech reservation changed.
3. During an eligible speaking turn, choose the clip and explicitly request transcription instead.
4. Compare Scribe's returned text with the caption, including names, deadlines and negation.

Pass: loading text uses the authored fixture directly and is clearly distinct from a paid Scribe result. Actual transcription returns provisional text and does not cast a vote or submit a contribution automatically.

## A07: Correct and commit a provisional transcript

1. Use one short selected recording during an eligible speaking turn and click its paid transcription control once.
2. Before committing, inspect the discussion history. The provisional text must not have appeared as a committed contribution.
3. Correct one word or punctuation mark in the editor. Commit while the seat remains eligible.
4. Compare the stored contribution with the reviewed editor text, not just the raw provider transcript.
5. If the turn expires before commit, wait for an eligible open discussion window. Do not count a failed commit as successful participation.

Pass: the reviewed text is committed only after your separate action, with the selected seat as author. The transcription itself remains advisory. Record the actual reservation and recognition errors; one successful clip does not establish accuracy for all recordings.

## A08: Try your microphone

1. Choose the five minute manual profile. Wait for your seat's discussion turn.
2. Click Record microphone and grant access if you want to test it.
3. Say: “Jeff will call IT before three PM. The backup has not been verified.” Stop after a few seconds. Recording stops automatically near 29 seconds.
4. Explicitly transcribe, then check the name, time and the word “not”. Correct the text and commit separately.
5. If microphone permission is denied, continue with typed text or a saved recording.

Pass: nothing is uploaded before transcription is requested; denial leaves a usable text path. Preserve a negation error as a quality failure even if the transcript otherwise looks plausible. This manual test does not claim your microphone, accent or room acoustics have already been validated.

## A09: Ask a live character

These controls are paid Vertex requests, separate from prerecorded playback. In the lobby or current MapleCart discussion, ask one question at a time.

| Character | Question | Review |
| --- | --- | --- |
| Facilitator | What should we clarify before deciding? | Relevant released evidence or a useful authored study question |
| IT | What technical facts are confirmed, and what remains unknown? | No invented restoration time or hidden later outcome |
| Journalist | What can we say publicly based on confirmed information? | No conversion of uncertainty into a confirmed disclosure |

Pass: the request visibly moves from pending to a reply or explicit failure. The reply has evidence IDs and model timing. It does not add a vote, advance the phase or change the metrics. Different roles may return the same authored evidence; record that as limited usefulness rather than inventing a stronger conversation result.

The current agent boundary selects authored evidence, rather than generating unrestricted dialogue. A prerecorded reply cannot substitute for a successful live model request when evaluating the agent.

## A10: Test tracking and participation

1. During an eligible turn, commit: “Jeff will call IT before 3 PM. Is the backup verified?”
2. Click the live extraction control for that committed contribution.
3. Check exact source spans for Jeff, call IT and 3 PM. Inspect every extra span as well as missing spans.
4. Compare participation counts with the committed contributions. Send ordinary room chat separately and check that it is not counted as a timed contribution.

Pass: source text and offsets match. Names and deadlines remain suggestions, not accepted assignments. An extra action span such as “verified” within a question needs review. A null confidence score is not a zero confidence result; this provider does not supply calibrated extraction confidence. Question counts are based on contribution text containing a question mark, not an emotion or personality model.

## A11: Ask each report's preparation agent

Select the relevant reference pack before asking. The audio library may provide spoken prompts, but the written question must still be sent through the preparation control to call the model.

| Pack | Question | Expected source |
| --- | --- | --- |
| T01 | According to BCP-4, what must IT verify before promising a restoration time? | `T01-BCP:BCP-4`: backup usability, dependencies and an estimate |
| T02 | According to CAMPAIGN-1, are gross ticket revenues or net proceeds donated? | `T02-CAMPAIGN:CAMPAIGN-1`: net proceeds after event costs |
| T03 | According to ACCESS-2, does appointing a director automatically provision payment access? | `T03-ACCESS:ACCESS-2`: finance must submit the recorded appointment |

Pass: the reply cites the selected pack and preserves its uncertainty. Ask a question about Priya while T02 is selected and check that the answer does not import T03 facts. Full questions and reviewer criteria are in [the report test guide](TEST_GUIDE.md).

T01, T02 and T03 are preparation reference packs, not complete playable timed scenarios in this app. The current game is MapleCart. Reviewer answers in these guides must never be added to participant retrieval.

## A12: Prepared voting and decision checking

1. Before voting, use Check decision. Expect no committed decision even if people have spoken or proposed an action.
2. During voting, select each seat and choose a prepared option. Change one seat's ballot before the deadline.
3. Verify that the change replaces that seat's vote rather than adding a fourth vote.
4. After resolution, check the decision again and inspect the exported history.

Pass: one vote per eligible member, no public tally during voting, one committed consequence after resolution. Spoken agreement, a model reply or fixture playback alone must not create a decision.

## A13: A winning custom proposal

Use a separate manual room. Saving a proposal is free; a custom proposal that wins invokes Vertex and consumes a reservation.

1. During discussion, save: “Isolate the compromised finance device, revoke its credentials, preserve evidence, and assign Jeff to report scope in 30 minutes while keeping unaffected checkout running.”
2. Vote for that custom option from all three seats.
3. Observe resolving, then the recorded consequence or an explicit unresolved result.
4. Check the returned explanation and the authored metrics. The model may select only an allowed outcome; the server applies it.

Pass for integration: the voted action is validated and committed once, or a provider failure remains visibly unresolved without an invented outcome. An unresolved result is not a successful model quality result. Mentioning Jeff does not record his separate acceptance of an assignment.

If resolution fails and the host Retry control is available, one explicit retry may be attempted within the original deadline after the earlier job finishes. Retrying is another paid attempt and does not extend the round. Do not create a failure by deleting keys or resetting budgets.

## A14: Tie, abstention and late participants

Use fresh rooms for these independent cases. The detailed view at <http://127.0.0.1:8788/> exposes additional membership controls if the audio lab does not show one.

1. Tie: cast one vote for each of three different prepared options, or have two seats choose different options while the third abstains. After voting closes, only the CEO may choose among the tied leaders. An untied option must be rejected.
2. Abstention: let all seats abstain in a separate room. Expect the authored no decision path rather than a fabricated majority.
3. Late join: join a running room from another independent browser session. The current electorate must not grow. The new member first becomes eligible at the next round boundary; this one round experiment has no second active round.

Pass: permissions and recorded reasons match the actual case. The single window lab polls its seats continuously, so it is not a reliable way to simulate a disconnected CEO. That boundary needs a separate session or an automated test clock.

## A15: Leave and rejoin without duplicating a seat

Use the detailed view in a separate manual test if the audio lab does not expose leave and recovery controls. Do not attempt to reclaim an actively polling audio lab seat while its original window remains open.

1. With local test name recovery enabled, leave explicitly, then rejoin with the same name and room code. If you close the tab instead, wait at least 30 seconds.
2. Verify the same member, role and previous ballot are preserved.
3. Check that the old credential no longer works and that the participant count did not increase.

This is a testing exception, not production identity verification. A server restart loses memory only rooms; name recovery cannot restore them.

## A16: Simultaneous review after the round

1. Finish one consequence and wait for the ended phase.
2. Explicitly request the three live character reviews together. This reserves up to US$0.15, so inspect the current balance first.
3. Record each question, answer, evidence ID, total request time and whether both parts of any compound question were answered.
4. Separately request a debrief if wanted. This is another paid request.

Pass: all replies refer only to committed history and released evidence. Submission together does not prove simultaneous provider execution. A reply that only repeats the consequence may be accurate but partly useful if you also asked what to clarify next. The debrief must not invent a second round or a recovered system.

## A17: Budgets, unavailable services and export

1. Check the displayed remaining balances before and after a free replay, one live request or one transcription. Record the difference.
2. If a cap or provider error occurs naturally, keep the exact error and continue with typed input and available recordings. Do not repeatedly retry or bypass the ledger.
3. Export the session. Check contributions, decisions, model jobs, timings and recording events.
4. Verify that the export contains no API keys or seat authentication tokens. Public member IDs are expected.

Pass: free replay remains free, paid attempts are visible, and model or speech failure does not silently advance the game. The export distinguishes scripted fixtures, reviewed speech and live model results. Budget exhaustion is not a model factual answer; record it as Blocked.
